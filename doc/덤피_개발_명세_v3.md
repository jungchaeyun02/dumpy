# 덤피(Dumpy) 개발 명세 v3 — 토스 미니앱 + 웹 (보안 반영)

> 두 곳에 서비스한다. **토스 미니앱**과 **웹**은 별개의 서비스지만, 속(데이터 구조·분류 규칙·서버)은 하나를 공유한다.
> v2에서 보안·개인정보·검수 규격을 보강한 판이다. 바뀐 부분은 [14. v2에서 바뀐 것](#14-v2에서-바뀐-것)에 모아뒀다.

---

## 0. 이 문서 쓰는 법

| 만들려는 것 | 읽을 부분 |
|---|---|
| 토스 미니앱 | 1~4장 + **5장(A)** + 7~13장 |
| 웹 | 1~4장 + **6장(B)** + 7~13장 |
| 서버·분류 엔진 | 1~4장 + **9장(보안)** |

**9장은 어느 쪽을 만들든 반드시 읽는다.** 여기 있는 항목은 나중에 붙이는 게 아니라 처음부터 들어가야 하는 것들이다.

---

## 1. 제품 정의

**덤피(Dumpy)** — 기록 시점에는 아무것도 요구하지 않고, 저장된 내용을 성격별로 자동 분류해 칸마다 다른 형태로 보여주는 메모 서비스.

- 타겟: 10~20대 학생
- 슬로건: **생각날 땐 고민 없이 그냥 덤프(Dump)해!**
- 이번 단계 검증 대상: **자동 분류의 유효성 하나.**

---

## 2. 절대 원칙

판단이 갈릴 때는 항상 이것들이 이긴다. **두 서비스 모두에 적용된다.**

1. **기록 시점에 아무것도 묻지 않는다.**
2. **저장은 분류를 기다리지 않는다.**
3. **분류 수정 경로는 항상 한 번의 동작 안에 있다.**
4. **`그 외` 칸은 절대 없애지 않는다.**
5. **칸마다 표시 방식이 실제로 달라야 한다.**
6. **칸을 탭으로 나누지 않는다.** 화면 좁은 미니앱에서 가장 쉬운 유혹이 탭인데, 나누는 순간 이 제품은 폴더 앱이 된다.
7. **남의 메모가 보이는 일은 절대 없어야 한다.** (v3 추가) 다른 원칙과 부딪히면 이게 이긴다. 일기가 들어가는 앱에서 이건 버그가 아니라 사고다.

## 3. 두 서비스의 관계

```
                  ┌──────────────────────┐
                  │   공통 서버 (코어)    │
                  │  · 분류 엔진          │
                  │  · 데이터 창고        │
                  │  · API + 인증/인가    │
                  └──────────┬───────────┘
                     ┌───────┴───────┐
            ┌────────▼──────┐  ┌─────▼─────────┐
            │ 토스 미니앱    │  │ 웹            │
            │ 모바일 세로    │  │ 데스크톱 넓게  │
            │ 토스 인증      │  │ 소셜 로그인    │
            │ 토큰 세션      │  │ 쿠키 세션      │
            └───────────────┘  └───────────────┘
```

- **공유**: 데이터 구조, 분류 규칙, API, 브랜드, 화면 문구, 보안 규칙
- **다름**: 화면 배치, 로그인 방식, **세션 유지 방식**, 조작 방법
- **계정은 잇지 않는다.** 나중에 이을 수 있게 자리만 남겨둔다(`provider`).

## 4. 공통 코어

### 4-1. 데이터 구조

**이용자(User)**

| 항목 | 설명 |
|---|---|
| `id` | 우리 서비스 안에서의 이용자 번호 |
| `provider` | `toss` \| `web` |
| `providerUserId` | **서버가 직접 검증해서 받아낸** 식별자 |
| `agreedAt` | 약관·개인정보 처리방침에 동의한 시각 |
| `ageConfirmedAt` | 만 14세 이상임을 확인한 시각 |
| `createdAt` | 가입 시각 |

**메모(Memo)**

| 항목 | 형태 | 설명 |
|---|---|---|
| `id` | 문자열 | 메모 고유 번호 |
| `userId` | 문자열 | **누구의 메모인지** |
| `content` | 문자열 | 본문. 빈 값 불가, **최대 5,000자** |
| `category` | `할일`\|`일기`\|`모아둔것`\|`그외` | 현재 들어 있는 칸 |
| `classifiedBy` | `auto`\|`manual` | 이 칸을 누가 정했는지 |
| `autoCategory` | 4개 중 하나 (비어 있을 수 있음) | 자동 분류가 원래 제안했던 칸 |
| `confidence` | 0~1 | 자동 분류의 확신도 |
| `hasDeadline` | 참/거짓 | 기한 표현이 감지됐는지 |
| `isDone` | 참/거짓 | 완료 여부. **`할일` 칸에서만 의미 있음** |
| `doneAt` | 시각 | 완료 시각 |
| `createdAt` / `updatedAt` | 시각 | 만든 / 마지막 수정 시각 |
| `deletedAt` | 시각 | 지운 시각 |

**반드시 지킬 것**

- **모든 조회에 `userId` 조건이 들어가야 한다.** 자세한 방법은 9-2에 있다.
- **`autoCategory`는 한 번 쓰면 덮어쓰지 않는다.** 이용자가 칸을 고쳐도 `category`만 바뀐다. 이래야 "자동 분류가 틀린 사례"가 쌓이고 3단계 개선의 재료가 된다.
- **칸을 옮겨도 `id`는 그대로.**
- **개별 메모 삭제는 실제로 지우지 않는다.** `deletedAt`만 기록하고 30일 뒤 완전 삭제. **단, 회원 탈퇴는 다르다.** (10-3 참고)

### 4-2. 자동 분류 규칙

규칙 기반이란 AI 모델 없이 **미리 적어둔 조건표대로 판단하는 방식**이다. 만들기 쉽고, 왜 그 칸에 갔는지 설명이 되고, 틀렸을 때 어디를 고칠지 바로 보인다.

**판정 순서 (위에서부터, 걸리면 멈춤)**

**1) 할 일 신호 → `할일`**
- 행동 어미: `~하기`, `~사기`, `~보내기`, `~챙기기`, `~해야`, `~가야`, `~할 것`
- 행동 명사: `제출`, `마감`, `신청`, `예약`, `결제`, `전화`, `확인`, `준비`, `등록`, `반납`
- 기한 표현이 있으면서 서술형이 아닌 경우

**2) 주소(URL) 또는 수집 신호 → `모아둔것`**
- `http://` 또는 `https://` 포함
- `추천`, `보고 싶은`, `읽을`, `듣고 싶은`, `가보고 싶은`, `위시`, `리스트`, `모음`

**3) 과거형 + 감정·서술 신호 → `일기`**
- 과거형 종결: `~했다`, `~였다`, `~았다`, `~었다`, `~더라`, `~네`
- 감정어: `기분`, `좋았`, `짜증`, `슬펐`, `행복`, `피곤`, `설렜`, `힘들`

**4) 아무것도 안 걸리면 → `그외`**

**기한 표현 목록** (`hasDeadline` 판정에도 사용)
`오늘`, `내일`, `모레`, `이번 주`, `다음 주`, `주말`, 요일 이름, `N월 N일`, `N일까지`, `~까지`, 시각 표현

**확신도**: 신호 2개 이상 `0.9` / 1개 `0.6` / 없음 `0.2`. 이번 단계에서는 저장만 하고 화면에 쓰지 않는다.

**규칙은 `lib/classify/rules.ts` 한 파일에 모은다.**

### 4-3. API

| 하는 일 | 방식 / 주소 | 보내는 것 | 받는 것 |
|---|---|---|---|
| 메모 저장 | `POST /api/memos` | `content`, `category`(선택) | 메모 전체 |
| 전체 목록 | `GET /api/memos` | — | 칸별로 묶인 목록 |
| 칸 바꾸기 | `PATCH /api/memos/:id` | `category` | 바뀐 메모 |
| 본문 수정 | `PATCH /api/memos/:id` | `content` | 바뀐 메모 |
| 완료 / 되돌리기 | `PATCH /api/memos/:id` | `isDone` | 바뀐 메모 |
| 삭제 | `DELETE /api/memos/:id` | — | 성공 여부 |
| 완료함 | `GET /api/memos/done` | — | 완료된 메모 목록 |
| **회원 탈퇴** | `DELETE /api/me` | — | 성공 여부 |

**모든 요청은 서버가 세션에서 꺼낸 `userId`로 동작한다. 클라이언트가 보낸 `userId`는 어떤 경우에도 쓰지 않는다.**

### 4-4. 기술 스택

| 무엇 | 역할 | 선택 |
|---|---|---|
| 화면 틀 | 페이지 뼈대와 화면 전환 | **Next.js (App Router)** |
| 언어 | 오타·실수를 미리 잡아줌 | **TypeScript** |
| 디자인 도구 | 색·여백·크기를 코드 옆에 적는 방식 | **Tailwind CSS** |
| 저장 창고 | 메모를 쌓아두는 곳 | **PostgreSQL** (SSL 연결 필수) |
| 창고 다루는 도구 | 넣고 빼는 명령을 쉽게 써줌 | **Prisma** |
| 분류가 도는 곳 | 규칙을 돌려 칸을 정하는 자리 | **서버 라우트** (`app/api/...`) |

- 분류는 **반드시 서버에서** 돈다.
- 토스 미니앱은 **WebView 방식**으로 올린다.
- **모든 통신은 HTTPS.** 토스 앱 안에서는 HTTP 기반 API가 아예 차단된다.

## 5. (A) 토스 미니앱

### 5-1. 전제

토스 앱 안에서 열리는 **모바일 화면**이다. 설치 개념이 없고, 물리 키보드가 없고, 화면이 좁다.

### 5-2. 인증 — **여기가 가장 중요하다**

#### 하면 안 되는 것

클라이언트(웹뷰)가 "나는 이 사람이야" 하고 식별자를 보내면, 서버가 그걸 믿고 메모를 꺼내주는 구조. **이렇게 만들면 식별자만 바꿔치기해서 남의 일기를 통째로 볼 수 있다.** 혼자 테스트할 땐 아무 문제 없어 보이기 때문에 놓치기 쉽다.

#### 해야 하는 것

```
① 웹뷰: 토스에서 인증 코드/토큰을 받는다
       ↓ (코드/토큰만 보냄. 식별자는 안 보냄)
② 우리 서버: 토스 서버에 직접 물어본다 (mTLS)
       ↓
③ 토스 서버: 검증된 식별자를 돌려준다
       ↓
④ 우리 서버: 이 식별자로 User를 찾거나 만들고, 세션을 발급한다
```

**식별자는 반드시 ②③을 거쳐 서버가 직접 받아낸 값만 쓴다.**

#### 세션은 쿠키가 아니라 토큰으로

일반적인 웹이라면 `HttpOnly` 쿠키가 정석이다. **그런데 토스 미니앱에서는 쓰면 안 된다.** iOS 13.4 이상에서 서드파티 쿠키가 완전히 차단되기 때문에, 쿠키 기반 로그인은 iPhone 이용자에게서 그냥 동작하지 않는다. 토스 문서도 쿠키 대신 토큰 방식을 쓰라고 안내한다.

- 서명된 토큰(JWT 등)을 발급해 클라이언트가 보관하고, 요청 헤더에 실어 보낸다
- 토큰 유효기간을 둔다 (예: 30일)
- 토큰 서명 키는 환경변수로 관리한다

#### mTLS 준비

앱인토스 서버 API를 부르려면 **mTLS(서로 인증서를 확인하는 통신)** 설정이 필요하다. 콘솔에서 인증서와 키 파일을 발급받아 서버에 넣는다.

- 인증서·키 파일은 **절대 Git에 올리지 않는다.** 유출되면 남이 우리 앱인 척 API를 부를 수 있다
- 서버에서 HTTPS 443 포트가 열려 있어야 한다
- 서버리스 환경(Vercel Edge, Supabase Edge Function 등)에서는 mTLS 설정이 까다롭다는 사례가 커뮤니티에 여러 건 올라와 있다. **처음부터 일반 Node 서버로 가는 게 안전하다**

#### 어떤 식별자를 쓸지 — 결정 필요

두 가지 방식이 있다.

| 방식 | 받는 것 | 장점 | 단점 |
|---|---|---|---|
| **토스 로그인** | 식별 키 (이름·번호·생년월일 등은 콘솔에서 전부 끔) | 기기를 바꿔도 이어짐 | 로그인 동의 화면을 거쳐야 함 |
| **익명 식별키** | 익명 키만 | 개인정보 수집이 더 적음, 진입이 빠름 | 이어지는 범위를 문서에서 확인해야 함 |

덤피는 이름도 이메일도 쓸 데가 없어서 **익명 식별키 쪽이 원칙에 더 맞는다.** 다만 기기를 바꿨을 때 메모가 따라오는지가 관건이라, 개발자센터의 사용자 식별키 문서를 먼저 확인하고 정한다. 어느 쪽을 쓰든 **서버 검증 API를 반드시 거친다.**

> 어느 경우든 이름·휴대폰 번호·생년월일·성별·이메일은 받지 않는다. 일기까지 담는 앱이 전화번호를 물으면 첫 화면에서 이용자가 나간다. 안 받는 것 자체가 이 제품에서는 기능이다.

### 5-3. 화면 배치 — 세로 스택

탭으로 나누지 않는다(원칙 6). 4칸을 세로로 쌓되 **각 칸의 최근 항목을 2개씩 미리 보여준다.**

```
┌──────────────────────────┐
│ ← [로고] 덤피            │  ← 토스가 그려줌. 직접 만들지 않는다
├──────────────────────────┤
│ [할일][일기][모음][그외] │  ← 분류 칩 (선택 안 해도 됨)
│ ┌──────────────────────┐ │
│ │ 여기다 쏙 던져!       │ │  ← 진입 시 커서
│ └──────────────────────┘ │
│                  [ 덤프! ]│
├──────────────────────────┤
│ 할 일               3개 › │
│  ☐ 내일까지 과제 제출     │
│  ☐ 우산 사기             │
├──────────────────────────┤
│ 일기                2개 › │
│  07.29  오늘 비 왔다...  │
├──────────────────────────┤
│ 모아둔 것           5개 › │
│  ▢ 카드   ▢ 카드         │
├──────────────────────────┤
│ 그 외               1개 › │
│  · 어쩌구                │
└──────────────────────────┘
```

- 칸 제목 옆 `›`로 그 칸만 전체로 볼 수 있다. **들어가는 건 되지만 기본 화면이 되면 안 된다.**
- 칸이 비어도 칸 자체는 숨기지 않는다. 4칸이 있다는 사실이 이 제품의 설명이다.
- 입력창은 상단 고정.
- 하단에 개인정보 처리방침·이용약관 링크와 탈퇴 진입점을 둔다.

### 5-4. 조작

- 저장: **`덤프!` 버튼.** 단축키 없음
- 분류 수정: 메모를 눌러 열리는 화면에서 칸 선택. 드래그는 쓰지 않는다
- 저장 직후 5초간 하단에 `'할 일'에 쏙 넣었어!` + `아니야, 딴 칸`

### 5-5. 앱인토스 검수 대응

| 항목 | 해야 할 것 |
|---|---|
| 내비게이션 바 | 앱인토스 비게임 내비게이션 바를 쓴다. 상단 로고 줄을 직접 만들지 않는다 |
| 뒤로가기 | 토스가 그려주는 뒤로가기와 자체 뒤로가기가 동시에 보이면 안 된다 |
| 나가기 | 모든 화면에서 미니앱을 나갈 수 있어야 한다 |
| 테마 | 라이트 모드로만 만든다 |
| 반응 속도 | 스크롤·터치·화면 전환이 2초 이상 지연되면 안 된다 |
| 데이터 유지 | 껐다 다시 들어와도 메모가 그대로 있어야 한다 |
| Safe Area | 상하단 여백을 침범하지 않는다. iOS Dynamic Island와 하단 홈 인디케이터 영역 포함 |
| 확대·축소 | 제스처 확대·축소를 끈다 |
| 바텀시트 | 진입하자마자 자동으로 뜨게 하지 않는다 |
| 버튼 이름 | 누르면 무슨 일이 일어나는지 예측되어야 한다 |
| 문구 | 비속어·은어·과도한 유행어를 쓰지 않는다 (7장) |
| 통신 | HTTPS만. HTTP는 토스 앱 안에서 차단된다 |

### 5-6. 설정 파일 규격 — 반려 단골

`granite.config.ts`의 값과 콘솔에 등록한 값이 **글자 하나까지 같아야 한다.** 커뮤니티에 이것 때문에 반복 반려됐다는 글이 여러 건 있다.

| 값 | 규칙 |
|---|---|
| `appName` | 콘솔 앱 이름과 완전히 일치. 소문자·숫자·대시만 (예: `dumpy`) |
| `brand.displayName` | 화면에 노출될 한글 이름 (예: `덤피`) |
| `brand.primaryColor` | `#FF6B1A` |
| `brand.icon` | **콘솔에 업로드한 아이콘과 같은 URL.** 다르면 반려된다 |

`appName`은 `intoss://{appName}` 형태의 딥링크에도 쓰인다. 한글이나 대문자를 넣으면 안 되는 이유가 이것이다.

### 5-7. 번들 용량

앱 번들은 **100MB 이하**여야 한다. 텍스트 앱이라 여유롭지만, 글꼴이 용량을 많이 먹는다.

- 한글 글꼴은 **서브셋**을 만들어 넣는다. 한글 전체 글자를 다 넣으면 파일 하나가 수 MB다
- 글꼴은 **WOFF2**, 이미지는 **WebP**
- 캐릭터 이미지는 번들에 넣지 말고 CDN에서 받아온다

### 5-8. 외부 유도 금지

웹 버전을 따로 서비스하니까 "웹에서도 쓸 수 있어요"를 넣고 싶어지는데, **자사 서비스 유도로 반려된다.**

- 미니앱 안에는 웹 버전 얘기를 **한 글자도 넣지 않는다**
- 코드에 남은 `window.open`, 외부 스킴, SNS 공유 링크도 전부 제거한다. 화면에 안 보여도 코드에 있으면 걸린다
- 공유 기능이 필요하면 `intoss-private://`가 아니라 `intoss://` 스킴을 쓴다

### 5-9. 등록 절차

1. 앱인토스 콘솔 가입 — **만 19세 이상, 본인 명의 토스앱 필요**
2. 워크스페이스 생성 → 앱 등록
3. mTLS 인증서 발급 (콘솔 → mTLS 인증서 탭)
4. 앱 정보 입력 — 이름은 간결하되 서비스 성격이 드러나게. `덤피`만으로는 메모 앱인 줄 모르니 부제를 붙인다
5. 키워드 최대 10개 — 타사 상표·서비스명이 들어가면 반려
6. 피처(앱 내 기능) 등록 — 1개 이상, 최대 3개
7. 토스 앱에서 최종 테스트 (출시 전에는 QR 코드 테스트 스킴 사용)
8. 콘솔에서 검토 요청 (영업일 기준 1~2일)

- 사업자 등록이 없어도 출시는 가능하다. 광고·결제로 수익을 낼 때만 필요하다
- **가이드와 체크리스트는 수시로 바뀐다.** 붙기 전에 개발자센터 비게임 체크리스트를 직접 훑는다

## 6. (B) 웹

### 6-1. 전제

웹은 **화면이 넓고 키보드가 있다.** 이게 유일한 강점이고, 여기서만 할 수 있는 걸 해야 한다.

### 6-2. 로그인

소셜 로그인 **하나만** 붙인다. 타겟이 10~20대 학생이라 카카오가 무난하다. 이메일·비밀번호 방식은 만들지 않는다 — 비밀번호 찾기, 잠금, 유출 대응까지 전부 따라와서 혼자 감당하기 어렵다.

미니앱과 원칙은 똑같다. **클라이언트가 보낸 식별자를 믿지 않고, 서버가 소셜 인증 서버에 직접 물어 검증한 값만 쓴다.**

**웹은 세션을 쿠키로 한다.** 자체 도메인이라 서드파티 쿠키 차단에 걸리지 않는다.

- `HttpOnly` — 자바스크립트가 쿠키를 못 읽게 한다 (스크립트가 심어져도 세션을 훔칠 수 없다)
- `Secure` — HTTPS에서만 전송
- `SameSite=Lax` — 다른 사이트에서 우리 API를 몰래 부르는 걸 막는다

### 6-3. 화면 배치 — 4칸 동시 노출

```
┌──────────────────────────────────────────────────┐
│  로고(DUMPY + 덤피)         생각날 땐 그냥 덤프해! │
├──────────────────────────────────────────────────┤
│  [할 일] [일기] [모아둔 것] [그 외]   ← 분류 칩   │
│  ┌────────────────────────────────────────────┐  │
│  │ 여기다 쏙 던져!                             │  │  ← 진입 시 커서
│  └────────────────────────────────────────────┘  │
│                            Ctrl+Enter로 덤프      │
├──────────────────────────────────────────────────┤
│  ┌───────────────────┐  ┌───────────────────┐    │
│  │ 할 일             │  │ 일기              │    │
│  │  기한 있음        │  │ 07.29             │    │
│  │  ☐ 과제 제출      │  │ 오늘 비 왔다...   │    │
│  │  언젠가           │  │                   │    │
│  │  ☐ 우산 사기      │  │                   │    │
│  └───────────────────┘  └───────────────────┘    │
│  ┌───────────────────┐  ┌───────────────────┐    │
│  │ 모아둔 것         │  │ 그 외             │    │
│  │ ▢카드  ▢카드      │  │ · 어쩌구         │    │
│  └───────────────────┘  └───────────────────┘    │
└──────────────────────────────────────────────────┘
```

4칸이 처음부터 나란히 보인다. 리포트가 웹을 고른 근거이자, **가치를 첫날에 보여주는 장치**다. 메모가 수백 개 쌓여야 분류의 고마움을 느끼는 구조면 그 전에 이용자가 떠난다.

각 칸은 최근 8개까지 보여주고 더 있으면 `N개 더 있어`. 하단에 개인정보 처리방침·이용약관 링크와 탈퇴 진입점.

### 6-4. 웹에서만 하는 것

- **저장 단축키** `Ctrl/Cmd + Enter`. 그냥 `Enter`는 줄바꿈
- **`N` 키**로 어디서든 입력창에 커서
- **PWA로 설치 가능하게** (`manifest.json` + 아이콘 + 최소 서비스워커)
- 모바일 폭에서는 4칸을 세로로 쌓는다. **입력은 폰에서도 반드시 동작해야 한다**

### 6-5. 웹에서는 미니앱을 언급해도 된다

미니앱 쪽은 외부 유도가 금지지만 웹은 우리 서비스라 제약이 없다. **한쪽 방향으로만 열린 문이다.**

## 7. 화면 문구

**두 서비스가 같은 문구를 쓴다.** 문구 세트를 둘로 나누면 관리도 두 배고 브랜드도 갈라진다. **미니앱 검수 기준(비속어·은어·과도한 유행어 금지)에 맞춰 한 벌만 만들고 웹도 그걸 쓴다.**

말하는 사람은 **덤피(햄스터)**다. 볼에 메모를 채운다는 콘셉트에서 온 단어(`쏙`, `모아두다`, `맡아두다`)를 쓰되 남발하지 않는다.

| 자리 | 문구 |
|---|---|
| 입력창 안내 | `여기다 쏙 던져!` |
| 저장 버튼 | `덤프!` |
| 저장 직후 | `'할 일'에 쏙 넣었어!` + `아니야, 딴 칸` |
| 처음 들어왔을 때 | `분류는 신경 쓰지 말고 그냥 던져. 덤피가 알아서 나눠줄게` |
| 칸이 비었을 때 (할 일) | `할 일이 하나도 없네! 개운하다` |
| 칸이 비었을 때 (일기) | `오늘 어땠어? 한 줄만 써봐` |
| 칸이 비었을 때 (모아둔 것) | `나중에 볼 거 여기다 모아둬` |
| 칸이 비었을 때 (그 외) | `어디에도 안 들어가는 건 덤피가 맡아둘게` |
| 할 일 완료했을 때 | `하나 끝냈다!` |
| 완료함 링크 | `끝낸 것 보기` |
| 완료함 되돌리기 | `앗, 아직이야` |
| 칸에 더 있을 때 | `N개 더 있어` |
| 삭제 확인 | `진짜 버릴까? 되돌릴 수 없어` |
| 저장 실패 | `앗, 저장이 안 됐어. 한 번만 다시 눌러줘` |
| 글자 수 초과 | `너무 길어! 5,000자까지만 담을 수 있어` |
| 너무 자주 저장할 때 | `잠깐만, 조금 천천히 던져줘` |
| 탈퇴 확인 | `정말 나갈까? 메모가 전부 사라지고 되돌릴 수 없어` |

### 문구 쓸 때 지킬 것

- **귀엽다고 무슨 말인지 모르게 되면 안 된다.** `덤프!`는 되지만 `가자!`는 안 된다 (미니앱 검수 항목이기도 하다)
- **버튼 이름과 결과 문구를 맞춘다.** `덤프!`를 눌렀으니 `쏙 넣었어!`가 나온다
- **빈 화면은 뭘 하면 되는지 알려주는 자리다**
- **실패 문구는 사과하지 않는다.** `앗` 정도는 톤이라 괜찮지만 `죄송합니다`는 안 쓴다
- **느낌표는 한 화면에 두 개까지**
- **이모지는 문구에 넣지 않는다.** 귀여움은 캐릭터와 글꼴이 맡는다
- **반말로 통일한다**

노랑·주황은 **면적이 아니라 포인트로** 쓴다. 라이트 모드 기준이라 미니앱 요구사항과도 맞는다.

### 글꼴

- 제목·로고: **Cafe24 Ssurround**(한글) / **Fredoka**(영문)
- 본문: **Pretendard**
- 제목은 아주 크게, 본문은 아주 얌전하게. 굵기 차이를 극단적으로 벌린다
- **미니앱은 서브셋 + WOFF2로 넣는다** (5-7 참고)

### 모양

- 모서리 반지름 크게(16~24px). 칩과 버튼은 완전한 알약 모양
- 그림자는 흐릿하게 퍼뜨리지 말고 살짝 어긋난 단단한 그림자로. 스티커가 붙어 있는 느낌

### 시그니처 — 저장할 때의 한 동작

**보낸 메모가 덤피의 볼로 빨려 들어갔다가 해당 칸에서 튀어나온다.**

효과를 여기저기 넣지 말고 **이 한 동작에만** 힘을 준다.

- **0.4초 안에 끝나야 한다**
- 이 동작이 다음 입력을 막으면 안 된다 (원칙 2)
- 애니메이션 줄이기를 켠 이용자에게는 생략한다

### 캐릭터 이미지

기획 리포트의 캐릭터는 **임시 이미지**다. 미니앱은 브랜드 아이콘이 콘솔 등록본과 일치해야 하므로, 등록 전에 최종본이 필요하다. 600×600 PNG.

## 9. 보안

**이 장은 어느 쪽을 만들든 처음부터 들어간다.** 나중에 붙이려면 인증 구조를 통째로 다시 짜야 한다.

### 9-1. 인증 — 클라이언트가 보낸 신원을 믿지 않는다

이 문서에서 가장 중요한 한 줄이다. 미니앱은 5-2, 웹은 6-2에 자세히 적었다. 공통 규칙만 다시 적으면:

- 클라이언트는 **인증 코드나 토큰만** 보낸다. 식별자를 직접 보내지 않는다
- 서버가 인증 서버에 직접 물어 검증한 값만 `providerUserId`로 쓴다
- 세션은 미니앱=토큰, 웹=쿠키

### 9-2. 인가 — 남의 메모를 못 만지게

`userId`로 걸러내는 걸 각 API마다 손으로 쓰면 언젠가 한 군데를 빠뜨린다. **그 한 군데가 사고가 된다.**

- 창고에 접근하는 함수를 **한 파일에 모으고, `userId`를 반드시 받게 만든다.** 안 넘기면 코드가 아예 컴파일되지 않게
- `PATCH`, `DELETE`처럼 특정 메모를 지목하는 요청은 **가장 먼저** "이 메모의 주인이 지금 로그인한 사람인가"를 확인한다
- 남의 메모를 지목했을 때는 "권한 없음"이 아니라 **"없는 메모"로 응답한다.** "권한이 없다"고 알려주면 그 메모가 존재한다는 사실을 알려주는 셈이다

### 9-3. 입력값 검증

| 항목 | 규칙 |
|---|---|
| `content` 길이 | **최대 5,000자.** 서버에서 자른다. 화면 제한만 두면 소용없다 |
| `content` 빈 값 | 공백만 있는 것도 거부 |
| `category` | 정해진 4개 값이 아니면 거부 |
| 요청 본문 크기 | 서버에서 상한을 둔다 |

화면에서 막는 건 예의고, **서버에서 막는 게 보안이다.** 화면을 거치지 않고 API를 직접 부를 수 있다.

### 9-4. 요청 횟수 제한

메모 저장·수정 API에 이용자당 **분당 60회** 정도의 상한을 둔다. 이걸 안 두면 자동화 도구로 창고를 채워 서비스를 마비시킬 수 있다. 상한을 넘으면 `잠깐만, 조금 천천히 던져줘`.

### 9-5. 메모 본문 안전하게 보여주기

이용자가 메모에 스크립트를 넣어 저장할 수 있다. React가 기본적으로 막아주긴 하지만 조건이 있다.

- **메모 본문을 HTML로 해석해서 그리지 않는다.** React의 `dangerouslySetInnerHTML`은 쓰지 않는다
- 나중에 서식 있는 메모를 지원하게 되면 그때는 `DOMPurify` 같은 도구로 걸러야 한다. **지금은 그냥 안 만드는 게 답이다**
- `모아둔 것` 칸에서 링크를 자동으로 알아보게 만들 때 주의한다. `javascript:`로 시작하는 주소는 거른다

### 9-6. 비밀 값 관리

Git에 올라가면 안 되는 것들:

- mTLS 인증서와 키 파일
- 토스·카카오 API 시크릿
- 데이터베이스 접속 정보
- 세션 토큰 서명 키

전부 `.env`로 빼고 `.gitignore`에 넣는다. **이미 한 번이라도 올렸다면 지우는 것으로 끝나지 않는다.** 기록에 남으니 해당 키를 폐기하고 새로 발급받아야 한다.

### 9-7. 창고 보안

- PostgreSQL 연결에 **SSL을 켠다** (`sslmode=require`)
- 관리자 계정 비밀번호를 코드에 적지 않는다
- 백업을 켠다. 창고가 날아가면 이용자 일기가 전부 사라진다

### 9-8. 오류 추적 도구

오류 추적 도구(Sentry 등)를 붙이면 **메모 본문이 그대로 그 회사 서버에 쌓일 수 있다.** 일기가 들어가는 앱에서 이건 심각하다.

- 붙일 거면 **본문과 식별자를 마스킹**하도록 설정을 먼저 하고 붙인다
- 이번 단계에서는 **아예 안 붙이는 것도 좋은 선택이다**

## 10. 개인정보·약관·연령

### 10-1. 다루는 정보

- 로그인 식별자 (토스 식별 키 또는 익명 키 / 소셜 식별자)
- 이용자가 쓴 메모 본문
- 동의 시각, 연령 확인 시각

이게 전부다. 이름·연락처·생년월일은 받지 않는다.

### 10-2. 만 14세 미만

개인정보보호법상 만 14세 미만 아동의 개인정보를 수집하려면 **법정대리인 동의**가 필요하다. 타겟이 10~20대 학생이라 실제로 걸린다.

**가입 시 `[필수] 만 14세 이상입니다` 체크를 받고, 만 14세 이상만 이용 가능하게 한다.** 확인한 시각을 `ageConfirmedAt`에 남긴다.

만 14세 미만도 받으려면 보호자 동의 절차를 붙여야 하는데, 개발량이 크게 늘고 이번 단계 검증과 아무 상관이 없다.

### 10-3. 탈퇴와 파기 — 개별 삭제와 다르다

이 둘을 헷갈리면 안 된다.

| 상황 | 처리 |
|---|---|
| 메모 하나 삭제 | `deletedAt` 기록 → 화면에서 숨김 → **30일 뒤 완전 삭제** (실수 복구용) |
| **회원 탈퇴** | **즉시 완전 삭제.** 이용자 기록과 메모 전부를 실제로 지운다 |

법적으로 목적이 끝난 개인정보는 지체 없이 파기해야 한다. 탈퇴한 사람의 메모를 30일 들고 있는 건 근거가 없다.

- 탈퇴 버튼은 **찾을 수 있는 곳에** 둔다. 숨기면 그 자체가 문제가 된다
- 탈퇴 전 `정말 나갈까? 메모가 전부 사라지고 되돌릴 수 없어`로 한 번 확인받는다
- 30일 지난 삭제 메모를 실제로 지우는 **정기 작업**을 만든다. 안 만들면 `deletedAt`만 쌓이고 아무것도 안 지워진다

### 10-4. 처리방침과 약관

**개인정보 처리방침**과 **이용약관** 문서를 만들고, 양쪽 서비스 하단에 링크를 둔다. 미니앱은 이게 없으면 심사에서 걸린다.

처리방침에 들어갈 것: 무엇을 받는지, 어디에 쓰는지, 얼마나 보관하는지, 어떻게 지우는지, 어디에 맡겨 두는지(호스팅·데이터베이스 업체), 문의처.

### 10-5. 메모 본문에 대해 이용자에게 할 말

v2에서 `메모는 밖으로 나가지 않아`라고 쓰려 했는데, **엄밀히 말하면 사실이 아니다.** 호스팅 업체와 데이터베이스 업체의 서버에는 당연히 저장된다. 정확한 표현으로 바꾼다.

> `메모를 분류하려고 다른 회사에 보내지 않아. 분류는 덤피가 직접 해.`

이건 사실이다. 이번 단계는 규칙 기반이라 외부 AI를 호출하지 않는다. 3단계에서 AI 분류를 도입하면 상황이 바뀌므로, 그때는 (1) 본문이 외부로 전송된다는 고지, (2) 분류 후 원문 미보관, (3) 개선 학습 사용 동의 — 세 가지를 함께 넣고 **이 문구도 반드시 바꾼다.**

> 이용자에게 하는 약속은 지킬 수 있는 만큼만 한다. 지키지 못할 약속은 안 하느니만 못하다.

## 11. 완료 조건

### 보안 (양쪽 공통, 가장 먼저 확인)

- [ ] 클라이언트가 보낸 식별자로 메모를 조회하는 코드가 **한 줄도 없다**
- [ ] 식별자는 서버가 인증 서버에 직접 물어 받은 값만 쓴다
- [ ] 계정 A로 로그인한 상태에서 계정 B의 메모 `id`를 지목해도 아무것도 안 나온다
- [ ] 5,000자를 넘는 본문을 API로 직접 보내면 거부된다
- [ ] 분당 60회를 넘겨 저장하면 막힌다
- [ ] `.env`에 있어야 할 값이 코드나 Git 기록에 없다
- [ ] 데이터베이스 연결에 SSL이 켜져 있다

### 기능 (양쪽 공통)

- [ ] 로그인한 이용자의 메모만 보인다
- [ ] 칩을 아무것도 안 누르고 저장할 수 있다
- [ ] 저장하면 입력창이 즉시 비고, 서버 응답을 기다리지 않는다
- [ ] 칩을 누르고 저장하면 자동 분류가 돌지 않고 그 칸에 들어간다
- [ ] 4개 칸의 표시 방식이 실제로 서로 다르다
- [ ] 할 일 칸이 '기한 있음 / 언젠가'로 나뉜다
- [ ] 저장 직후 5초 안내에서 칸을 바꿀 수 있다
- [ ] 칸을 바꿔도 `autoCategory`가 그대로 남는다 (창고를 직접 열어 확인)
- [ ] 완료한 할 일이 완료함으로 가고 24시간 안에 되돌릴 수 있다
- [ ] 어느 규칙에도 안 걸리는 문장이 `그 외`로 간다
- [ ] 탈퇴하면 메모가 창고에서 실제로 사라진다
- [ ] 개인정보 처리방침·이용약관 링크가 보인다

### 미니앱

- [ ] iPhone에서 로그인이 유지된다 (쿠키가 아닌 토큰인지 확인)
- [ ] 4칸이 탭이 아니라 세로 스택으로, 스크롤 한 번에 다 보인다
- [ ] 껐다 다시 들어와도 메모가 그대로 있다
- [ ] 상하단 Safe Area를 침범하지 않는다
- [ ] 자체 뒤로가기와 토스 뒤로가기가 동시에 보이지 않는다
- [ ] 웹 버전을 언급하는 문구·링크가 **코드에도** 하나도 없다
- [ ] `granite.config.ts`의 `appName`·아이콘이 콘솔 등록값과 완전히 일치한다
- [ ] 번들이 100MB 이하다
- [ ] 어떤 조작도 2초 이상 걸리지 않는다

### 웹

- [ ] 주소를 열면 클릭 없이 바로 타이핑된다
- [ ] 4칸이 한 화면에 동시에 보인다
- [ ] `Ctrl/Cmd + Enter`로 저장되고 `N`으로 입력창에 간다
- [ ] 홈 화면에 설치된다 (PWA)
- [ ] 폰에서 열어도 입력과 저장이 된다
- [ ] 키보드만으로 저장·수정·완료가 된다

## 13. 먼저 확인해야 할 것

문서만으로 정할 수 없어서 개발자센터를 직접 봐야 하는 항목이다. **개발 시작 전에 확인한다.**

- [ ] **익명 식별키 vs 토스 로그인** — 기기를 바꿔도 메모가 따라오는지 (5-2)
- [ ] 식별자 서버 검증 API의 정확한 주소와 요청 형식
- [ ] mTLS를 쓸 서버 환경 결정 — 서버리스에서 문제 사례가 많으니 일반 Node 서버 권장
- [ ] 번들 용량 상한과 아이콘 규격의 현재 기준
- [ ] 비게임 출시 체크리스트 최신판

앱인토스 가이드는 수시로 바뀐다고 토스가 직접 밝히고 있고, 실제로 개발 도중 기준이 바뀌었다는 사례가 커뮤니티에 있다. **이 문서의 토스 관련 내용도 지금 시점 기준이다.**

## 14. v2에서 바뀐 것

| 항목 | v2 | v3 |
|---|---|---|
| 인증 | "토스 식별 키를 받아 넣는다" | **서버가 직접 검증해서 받아낸 값만 사용.** 클라이언트가 보낸 식별자는 절대 안 씀 |
| 세션 | 명시 없음 | **미니앱=토큰 / 웹=쿠키** (미니앱에서 쿠키는 iOS에서 동작 안 함) |
| mTLS | 없음 | **필수.** 앱인토스 서버 API를 부르려면 인증서 기반 통신 필요 |
| 인가 | "모든 조회에 `userId`" | 창고 접근 함수를 한 곳에 모아 강제, 소유권 검증, 없는 메모로 응답 |
| 입력 제한 | 없음 | 본문 5,000자, 요청 횟수 분당 60회 |
| 탈퇴 | 없음 | **탈퇴 기능 필수, 탈퇴 시 즉시 완전 삭제** (개별 삭제 30일과 구분) |
| 연령 | "정책이 필요하다" | 만 14세 이상 확인 체크박스, 확인 시각 기록 |
| 설정 파일 | 없음 | `granite.config.ts` 규격 — 반려 단골 |
| 번들 | 없음 | 100MB 이하, 글꼴 서브셋 |
| 오류 추적 | 없음 | 붙일 거면 마스킹 먼저. 안 붙여도 됨 |
| 안내 문구 | `메모는 밖으로 나가지 않아` | **`분류하려고 다른 회사에 보내지 않아`** — 앞의 표현은 사실이 아니었음 |
| 원칙 | 6개 | **7번 추가: 남의 메모가 보이는 일은 절대 없어야 한다** |

### 검토 의견 중 그대로 따르지 않은 것

- **세션 쿠키(`HttpOnly`/`Secure`/`SameSite=Lax`)** — 웹에는 그대로 적용했지만, **미니앱에는 적용하지 않았다.** 토스 앱 웹뷰에서는 iOS 13.4 이상에서 서드파티 쿠키가 완전히 차단되어 쿠키 기반 로그인이 동작하지 않는다. 토스 문서도 토큰 방식을 안내한다. 미니앱은 토큰으로 간다.
- **탈퇴 시 30일 유예 후 파기** — 개별 메모 삭제에만 30일을 두고, **탈퇴는 즉시 파기**로 했다. 탈퇴는 처리 목적이 끝난 경우라 지체 없이 파기하는 게 맞다.
